# Боты Mahaon v2 — отчёт ревью и задание на доработку

Дата ревью: 2026-11-12. Документ адресован исполнителю (Opus), который будет чинить.
Дизайн системы и статус этапов — `dev-docs/mahaon-bots-v2-design.md`, читать первым.

## 0. Как пользоваться отчётом

**Что проверено.** Прочитан целиком код `Projects/UOContent/Systems/Bots/` (~14 200 строк),
`Systems/MahaonBots/` (тело бота, гильдии, банк, отношения, репутация, слухи),
`Items/Misc/Mahaon/MahaonBotBeacon.cs`, навигация `Engines/Pathing/Nav/`
(`NavFollower`, `NavPathfinder`, `NavRouteWorker`), правки движка под ботов
(`Server/Maps/Map.cs`, `Spells/Base/Spell.cs`, `SpecialMove.cs`, `PlayerMobile.cs`,
`CityGuard.IsGuardTarget`).

**Что НЕ проверено** (там могут быть свои находки): внутренности `NavSearch`,
`NavGraphBuilder`, `NavLinks`, `NavSystem`; `CityControlSystem`, `CityGuard*`,
`MahaonRaids`, `AuctionHouseSystem`, `MahaonCityHouseSystem`, системы квестов
`MahaonQuests`; гамп маяка; мосты `MahaonAi`; сами тесты. Поведение на живом сервере не
наблюдалось — всё, кроме помеченного `[ТЕСТ]`, найдено чтением кода.

**Метки достоверности:**

- `[ТЕСТ]` — подтверждено запуском теста.
- `[КОД]` — путь исполнения прослежен по коду до конца, включая код движка.
- `[ГИПОТЕЗА]` — логика указывает на проблему, но зависит от данных шарда или не прослежена
  до конца. Сначала подтвердить, потом чинить.

**Номера строк** даны на момент ревью и поедут; рядом всегда имя метода.

**Правила работы в репозитории:**

- В рабочем дереве много незакоммиченной работы владельца (в т. ч. свежая — травничество:
  `HerbForageGoal.cs`, правки `FarmGoal`, `SupplyGoal`, `BotGoals`, `BotCrafting`,
  `BotMobile`). Ничего не сбрасывать и не «чистить». Коммитить только по просьбе владельца.
- Комментарии в коде — на русском, объясняют *почему*, а не что (так написан весь модуль).
- Перед правками прочитать `dev-docs/threading-model.md`, `timers.md`, `tick-counts.md`,
  `serialization.md`.
- На каждое исправление — тест в `Projects/UOContent.Tests/Tests/Systems/Bots/` (или
  `Projects/Server.Tests/Tests/Maps/` для движка). Сначала падающий тест, потом правка.
- Сохранения (`Distribution/Saves`) не трогать. Если меняется сериализация `BotBrain` —
  поднять версию и написать `MigrateFrom`.

## 1. Критичные (P0)

### B-01. Сектора впереди идущего бота не просыпаются `[ТЕСТ]`

**Где:** `Projects/Server/Maps/Map.cs` — `Map.OnMove` (~795–818), `Sector.OnEnter(Mobile)` (~1969–1981).

**Что происходит.** `OnMove` перед передачей мобиля делает `newSector.HoldActivation()`
(`_activators++`), чтобы пересечение не усыпляло перекрытие. Но `Sector.OnEnter` будит
окрестность только при `mob.ActivatesSectors && _activators++ == 0` — а после `Hold`
счётчик уже 1, условие ложно, `ActivateSectors` не вызывается. При этом `oldSector.OnLeave`
честно усыпляет всё, что вышло из радиуса. Итог: активная зона за ботом сжимается, а
впереди не растёт. Через 3 пересечения бот стоит в спящем секторе, через 5 вокруг него не
активно ничего. Сектора будятся только там, где бот появился через `MoveToWorld` (спавн,
врата, телепорт). Для мобилей с `NetState` ветка `OnEnter` будит безусловно, поэтому у
живого игрока бага нет.

**Последствие.** Это «причина №2» из дизайн-документа (§2, §3.2), которую v2 должен был
закрыть: вдали от точки появления бот охотится на спящих существ.

**Подтверждение.** Временный тест (в репозитории не оставлен) упал с сообщением
`leading edge asleep after 1 sector crossing(s)`:

```csharp
[Fact]
public void Activator_WalkingAcrossSectors_WakesSectorsAhead()
{
    var map = Map.Felucca;
    var mobile = new Activator();               // Mobile с ActivatesSectors => true
    var step = 1 << Map.SectorShift;
    var origin = new Point3D(3600, 3000, 0);    // подальше от точек других тестов

    try
    {
        mobile.MoveToWorld(origin, map);

        for (var i = 1; i <= 6; i++)
        {
            mobile.Location = new Point3D(origin.X + i * step, origin.Y, 0);

            Assert.True(map.GetSector(mobile.X + Map.SectorActiveRange * step, mobile.Y).Active,
                $"leading edge asleep after {i} sector crossing(s)");
            Assert.True(map.GetSector(mobile.X, mobile.Y).Active,
                $"own sector asleep after {i} sector crossing(s)");
        }
    }
    finally
    {
        mobile.Delete();
    }
}
```

**Как чинить.** В `OnMove`, когда `holds` и у мобиля нет `NetState`, после
`newSector.OnEnter(m)` явно вызвать `ActivateSectors(newSector.X, newSector.Y)`
(`Sector.Activate()` для уже активного сектора — no-op). Альтернатива — отдельный флаг
«удержание» вместо инкремента счётчика. Тест выше добавить в `SectorActivatorTests`.

**После правки замерить** стоимость: `DeactivateSectors` на каждое пересечение — до 25×25
проверок секторов (см. P-09).

### B-02. Счётчик неудач цели сбрасывается любым удачным шагом `[КОД]`

**Где:** `BotBrain.Think`, ветка `BotActionStatus.Done` (~257–262: `_goalFailures = 0`) и ветка
отказа (~284).

**Что происходит.** План почти всегда «дойти → сделать». `GoTo` завершается `Done` и
обнуляет `_goalFailures`; следующее действие даёт `Failed`, счётчик становится 1, цель
перепланируется, `GoTo` (бот уже на месте) снова `Done` — и так бесконечно. Порог «три
неудачи → цель на пятиминутную паузу» для многошаговых планов недостижим. Выйти можно
только если на обзоре целей другая цель обгонит текущую больше чем на `SwitchCost`.

**Примеры, где это срабатывает:**

- `HuntAction` при перегрузе и нуле убийств сразу `Failed` (`HuntAction.cs:74–77`).
- `GatherAction` при перегрузе — `Failed` и ещё штраф точке в атласе (`GatherGoal.cs:91–94`).
- `TameAction` — зверь отошёл дальше 3 тайлов → `Failed` «план вернётся» (`TameAction.cs:40–43`).
- `KillQuestGoal` с добычей не по силам (см. B-19).

**Как чинить.** Сбрасывать `_goalFailures` только при завершении цели (`_plan.Count == 0`).
Лучше — считать неудачи по цели в скользящем окне (`Dictionary<BotGoal, (int count, long since)>`),
чтобы чередование «успех шага / отказ шага» не обнуляло историю.

**Тест:** цель с планом `[всегда Done, всегда Failed]` — после трёх кругов цель должна уйти
на паузу.

### B-03. `[BecomeBot` распродаёт имущество игрока `[КОД]`

**Где:** `BotBank.TakeOut` (`Economy/BotBank.cs:43–74`), `BankGoal.Score` (`Goals/BankGoal.cs:18–21`),
`BotGoods.IsForSale` (`Economy/BotGoods.cs:56–62`), `DepositGoldAction.Tick`.

**Что происходит.** Мозг одержимого персонажа (`BotSystem.Possess`) — тот же, что у бота.

1. `BankGoal` помечена `IsUpkeep`, то есть работает и при заданном фокусе. Её оценка растёт
   от числа *любых* не-денежных предметов в банке (`WaitingGoods`).
2. `DepositGoldAction` вызывает `BotBank.TakeOut`, который выносит из банка всё, что не
   золото и не чек, сколько позволит вес, и помечает каждую вещь как добычу (`MarkLoot`).
3. Помеченное `IsForSale` отдаёт торговцам, остальное — на аукцион по `BaseUnitPrice`
   (оружие, броня, украшения — 30 золота за штуку).
4. Отдельно от банка: `IsRawGood` (слитки, руда, брёвна, доски, уголь, травы) и `IsProduct`
   (любая `PlayerConstructed` вещь, лежащая россыпью в сумке) продаются без всяких меток.

Для бота это задуманное поведение (в банке у него только возвраты с аукциона). Для живого
персонажа это потеря накопленного.

**Как чинить.** Минимум: для не-`BotMobile` отключить ветку «забрать товар из банка» и
продажу того, что мозг не добыл сам в этом сеансе одержимости. Правильнее — хранить явный
список «моё на продажу» (см. B-07) и не выводить продажность из типа предмета.

**Тест:** одержимый `PlayerMobile` с оружием в банке и слитками в сумке — после
`BankGoal`/`TradeGoal` всё на месте.

### B-04. Школы с порогом навыка 0: все боты колдуют без навыка и реагентов `[КОД]`

**Где:** таблица `BotSchools.Book` (`Combat/BotSchools.cs:44–69`), вызовы
`BotCombat.Fight` (~372) и `BotHealing.TryHeal` (~68).

**Что происходит.**

- `CurseWeaponSpell` записан как `Necromancy, MinSkill 0, Buff, шанс 0.3`. `RequiredSkill`
  у него в движке тоже 0.0 (`Spells/Necromancy/CurseWeapon.cs:25`), проверки навыка в
  `CheckCast` нет, реагент (`PigIron`) проверяется только в конце каста
  (`Spell.CheckSequence`, ~863). `BotSchools.TryCast` ни шанс, ни реагенты не смотрит.
  Значит любой бот в бою, включая воина с нулём некромантии, на 30% тиков (тик 300 мс)
  начинает каст 0,75 с, который заканчивается «More reagents are needed».
- Пока идёт каст, замах невозможен: `BaseWeapon.OnSwing` (~851) запрещает удар при
  `sp.IsCasting && sp.BlocksMovement`, а `Spell.BlocksMovement => IsCasting` (`Spell.cs:82`),
  некромантия его не переопределяет.
- `GiftOfRenewalSpell` записан как `Spellweaving, MinSkill 0, Heal`. Проверка квеста
  арканиста на шарде снята (`ArcanistSpell.CheckCast`), поэтому любой раненый бот ниже
  60% здоровья без подходящего лечения начинает каст на 3 секунды с шансом успеха около
  четверти при нулевом навыке.
- `NetherBoltSpell` — `Mysticism, MinSkill 0, Attack` — та же история у магов, когда
  магия не прошла.

Это, по всей видимости, и есть «толпа, беспрерывно фитилящая», которую уже чинили в
`BotSpellbook` для магии, — но таблицу школ правка не затронула.

**Как чинить.** В `BotSchools.TryCast` пропускать заклинание через `BotSpellbook.Usable`
(шанс ≥ 0.5, реагенты, запас маны). Пороги `MinSkill` поднять до осмысленных или убрать
вовсе, оставив решение `CastChance`. Для паладина учесть десятину.

**Тест:** воин с Necromancy 0 в бою за N тиков не начинает ни одного каста; маг без
реагентов не начинает каст, требующий реагентов.

### B-05. Лечение союзника заклинанием уходит в самого бота `[КОД]`

**Где:** `BotCombat.Think`, обработка курсора (`Combat/BotCombat.cs:73–81`);
`BotHealing.StartAllyHeal` / `TryHealAlly`.

**Что происходит.** Курсор с флагом `Beneficial` всегда получает целью самого бота:
`cursor.Invoke(bot, helps || ... ? bot : target)`. Подмена нужна мастерствам
(`BotMasteries.TryUse` передаёт врага и для полезных способностей), но ломает
`TryHealAlly`: Greater Heal, Cure и Close Wounds, начатые «на пациента», лечат лекаря.
`BotRelationships.OnHelped(patient, bot)` при этом записывается — отношения растут от
помощи, которой не было.

**Как чинить.** Подменять цель на себя только когда `target` не друг
(`!BotSocialRules.IsFriend(bot, target) && target != bot`). `OnHelped` вызывать после
фактического лечения.

**Тест:** в `BotPartyTests`/`BotCombatTests` — раненый член отряда, лекарь с Magery 80;
после каста здоровье выросло у пациента.

### B-06. ПК-боты не краснеют, а правила для них расходятся `[КОД]`

**Где:** `PlayerMobile.OnDeath` (~2765–2768: `killerBot.Kills = 0`), `CityGuard.IsGuardTarget`
(~371–376), `BotSocialRules.IsOutlaw` / `TownFor` (`BotSocialRules.cs:20, 34`),
`BountyHuntGoal`, `NavPathfinder.AccessOf`.

**Что происходит.**

- При гибели любого `PlayerMobile` от ПК-бота счётчик убийств убийцы обнуляется, и стоит
  это *до* `PlayerDeathEvent`, из которого идёт отчёт об убийстве. `Kills` не поднимается
  выше 1, `Murderer` (≥ 5) не наступает никогда. В дизайн-документе написано обратное
  («ПК честно краснеют»).
- Стража бьёт по флагу роли `IsPk`. Сам бот считает себя вне закона только по
  `Murderer || Criminal`. Когда криминальный флаг остыл, ПК-бот идёт в охраняемый город —
  в банк, продавать, за припасами, а при бегстве — «в город, где стража» (`BotCombat.Flee`),
  и гибнет от стражи.
- Охотник за головами (`BountyFightAction`) нападает на синего ПК-бота, сам получает
  `Criminal` и становится целью стражи.
- Логика «красный идёт к святыне/злому лекарю», запрет лунных врат убийцам — мёртвый код.

**Как чинить.** Убрать обнуление `Kills`. Выбрать один источник правды: либо ПК-бот
честно набирает убийства и всё ключуется на `Murderer`, либо `IsOutlaw` учитывает `IsPk`
(тогда и `Notoriety`, чтобы атака на него не была преступлением). Первый вариант
соответствует принципу «те же правила, что у игроков».

### B-07. После рестарта добыча перестаёт быть товаром; от хлама избавиться нечем `[КОД]`

**Где:** `BotBrain._loot`, `_lootedCorpses`, `OwnCorpse` (`BotBrain.cs:135–157`, всё
несериализуемое); `BotGoods.IsForSale` (последняя строка условия).

**Что происходит.** Оружие, броня, украшения, реагенты, шкуры с трупов продаются только
если помечены `MarkLoot`. Метка живёт в памяти. После перезапуска всё это лежит в сумке
«ничьим»: `ValueCarried` его не считает, `TradeGoal` даёт 0, а вес остаётся. Перегруженный
бот не может ни охотиться, ни добывать (см. примеры в B-02) и попадает в бесконечный цикл.
Сброса хлама (в банк, торговцу за бесценок, на землю) в системе нет вообще.

Там же: `OwnCorpse` теряется при рестарте — вещи на трупе пропадают; `_loot` не
ограничен по размеру.

**Как чинить.** Сохранять метки в `BotBrain` (список серийников, чистить от удалённых
при сохранении) вместе с `OwnCorpse`. Добавить цель-обслуживание «разгрузиться»: при
весе выше порога и нулевой продажной ценности — сдать лишнее в банк или выбросить.

## 2. Заметные баги (P1)

### B-08. Маг без доступных заклинаний стоит столбом; лучник без стрел — тоже `[КОД]`

`BotCombat.Fight`, ветка `Mage` (~394–401). Комментарий у `TryBest` обещает «идёт в
ближний бой (см. вызывающий код)», вызывающий код возвращает
`distance > KeepMax ? Approach(...) : FightTickMs` и ещё отступает при сближении
(`StepAway`). Маг без маны или реагентов держит дистанцию и не делает ничего до порога
бегства. У лучника стиль определяется только по оружию в руках (`BotCombatStyles.Of`),
наличие боеприпасов не проверяется. Чинить: при невозможности атаковать — сменить стиль на
рукопашный на этот бой либо уходить; `HuntGoal.Score` обнулять при пустом колчане/сумке
реагентов (снабжение их докупит).

### B-09. `GoToAction._replans` не сбрасывается при продвижении `[КОД]`

`Actions/GoToAction.cs:105, 139`. Лимит `MaxReplans = 3` действует на весь путь. Четыре
заминки (толпа в воротах, закрытая дверь, моб в коридоре — каждая это 6 отказов шага по
250 мс в `NavFollower`) на маршруте через континент — и поход провален. Сбрасывать счётчик,
когда `NavFollower.Index` вырос или дистанция до цели сократилась.

### B-10. Прибытие проверяется без учёта высоты `[КОД]`

`GoToAction.Tick` (~93): `bot.Map == TargetMap && Utility.InRange(bot.Location, TargetPoint, _range)` —
двумерная проверка. Бот этажом выше или ниже (мост, второй этаж банка, подземный ход)
считается дошедшим, следующее действие отказывает по дальности, и включается B-02.
В `NavFollower.Step` проверка по Z есть (`< 16`) — добавить такую же.

### B-11. Член отряда крутится вхолостую, если лидер на другой карте или мёртв `[КОД]`

`Social/FollowLeaderAction.cs:21`. При `leader.Map != bot.Map` или `!leader.Alive`
действие возвращает `Done`. Цель завершается, `FollowGroupGoal` (оценка 2.0, отряд не
распущен) тут же выигрывает снова, новое действие снова `Done`. Цикл с периодом 250 мс,
каждый круг — полный `ReviewGoal` по 52 целям. Для бота-лидера смерть распускает отряд
через `GroupHuntAction.Stop`, а для лидера-игрока — нет. Чинить: убрать проверку карты
(`GoToAction` по мобилю умеет идти между фасетами), при мёртвом лидере-игроке — ждать
(`Running`) либо выходить из отряда.

### B-12. `Goal == null` вызывает обзор целей на каждом шаге `[КОД]`

`BotBrain.Think` (~227): `if (now - _nextGoalReview >= 0 || Goal == null) ReviewGoal(now)`.
В `LastResort` план есть, а цели нет — значит пока бот идёт домой, он на каждом шаге
(200–400 мс) пересчитывает все цели. Ввести цель-заглушку для `LastResort` или проверять
`Goal == null && Action == null && _plan.Count == 0`.

### B-13. Боты добывают руду из воды `[КОД]`

`Economy/ResourceProbe.cs:86–96`: для руды годится любой тайл ландшафта с флагом
`Impassable`. У воды этот флаг тоже есть. Игроку путь закрыт в `HarvestTarget`
(`rock = Impassable && !Wet`, ~121–133, с комментарием про «руду из собственного пруда»),
а бот вызывает `MahaonMiningSwings.StartSurfaceSwings` напрямую, и та цель не проверяет.
Чинить: вынести предикат «это скала» в одно место и использовать в обоих путях.

### B-14. Снабжение: первая неудовлетворимая нужда блокирует все остальные `[КОД]` + `[ГИПОТЕЗА]`

`Goals/SupplyGoal.cs`, `TryNextConsumable` (77–217) и `Plan` (244–275). Метод возвращает
*первую* нехватку по фиксированному порядку. Если этот товар в городе никто не продаёт,
`Plan` возвращает `null`, цель уходит на паузу, через две минуты всё повторяется — а до
следующих пунктов списка (стрелы, корм животным, бутылки, зелья) очередь не доходит
никогда. `[ГИПОТЕЗА]`: насколько это часто — зависит от ассортимента лавок (кандидаты:
реагенты мистика, инструмент барда).

Там же `[КОД]`: `MainTrade` при нулевых навыках добычи возвращает «руда/кирка», поэтому
любой бот и одержимый персонаж без кирки получает оценку 0.9 «купить кирку».

Чинить: перебирать нужды, пока не найдётся та, что продаётся; инструмент добычи требовать
только при навыке выше порога.

### B-15. Действия без проверки продвижения `[КОД]`

- `SmeltAction` (`Economy/SmeltAction.cs:33–49`): берёт первую стопку руды и плавит.
  Если плавка отказала без расхода (`MahaonOre.SmeltTarget`: навык ниже требуемого,
  «не похоже на печь»), следующая итерация берёт ту же стопку — бесконечно, раз в 1,5 с.
- `PickFruitAction` (`Goals/FarmGoal.cs:208–213`): двойной щелчок по дереву, пока на нём
  есть плоды; если сбор не уменьшает `FruitRemaining` (перегруз, отказ) — бесконечно.

Чинить: счётчик попыток без изменения состояния → `Failed`.

### B-16. Самоцвет за каждую смерть кладётся без слияния стопок `[КОД]`

`GuildBank.OnMemberDeath` (`MahaonBots/GuildBank.cs:359–396`): `bank.DropItem(gem)`.
`DropItem` не сливает стопки (сливает `Deposit` через `StackWith`, но он самоцветы не
принимает). Каждая смерть бота в гильдии — новый предмет в мире. Расход есть
(`GuildUpgrades`, максимум 5 покупок на гильдию за всё время), после него рост
неограничен. Чинить: сливать со стопкой того же типа; ввести потолок.

### B-17. Титул репутации слетает при смерти `[КОД]`

`BotReputation.RefreshTitle` кеширует выставленный титул в `AppliedTitle`. `PlayerMobile.OnDeath`
делает `NameMod = null`. После смерти титула нет, а кеш говорит «уже стоит» — повторно он
появится только при переходе через порог. Также `NameMod` делят маскировка, инкогнито и
полиморф. Чинить: сверять с фактическим `NameMod`, переприменять в `Resurrect`.

### B-18. Вербовка в отряд без согласия `[КОД]`

`LeadGroupGoal.Plan` (`Goals/GroupGoals.cs:35–40`) берёт любого бота в 20 тайлах с боевым
навыком от 30 — в том числе занятого плавкой, идущего за своим трупом, уставшего или с
полной сумкой товара. `BotGroup.TryAdd` сбрасывает ему план. `FollowGroupGoal` весит 2.0 и
перебивает отдых, укрытие от набега и возврат к трупу. Кроме того, `Plan` создаёт отряд и
рвёт чужие планы *до* того, как выяснит, есть ли куда идти (`spot == null` → `Disband`).
Чинить: рекрут соглашается сам (его оценка «пойти» против текущей цели), исключить
цели-обслуживание и раненых; сначала искать место, потом собирать.

### B-19. Задание на убийство не по силам — вечное блуждание `[КОД]`

`KillQuestGoal` (`Goals/KillQuestGoals.cs:143–146, 185–190`) не сравнивает славу добычи с
`MaxPreyFame`. `HuntAction.FindPrey` такую добычу не выберет, действие 25 минут ходит по
месту и отказывает, а из-за B-02 цель перепланируется бесконечно. Чинить: при взятии и в
оценке проверять, что вид по силам; иначе отказываться от задания.

### B-20. Свой труп: недобранное бросается `[КОД]`

`LootCorpseAction.Tick` (`Combat/LootCorpseAction.cs:57–78`): цикл прерывается на первом
предмете, который не влез, после чего `OwnCorpse = null`. Остальное имущество бот больше
не ищет.

### B-21. Исключение в оценке одной цели парализует бота `[КОД]`

`BotScheduler.Drain` (~79–89) ловит исключение из `Think`, сбрасывает план и будит бота
через 5 с. Но если бросает `Score` какой-то цели, `ReviewGoal` обрывается на ней каждый
раз — бот не делает ничего и раз в 5 секунд пишет ошибку в лог, без ограничения. Это не
теория: три упавших теста (T-01) идут ровно этим путём. Кроме того, `brain.ClearPlan()`
внутри `catch` сам не защищён.

Чинить: `try/catch` вокруг `goal.Score`/`goal.Plan` в `ReviewGoal` с паузой для
провинившейся цели и ограничением частоты записи в лог.

### B-22. Сбор ресурсов без порога навыка `[КОД]`

`GatherGoal.Score` (`Goals/GatherGoal.cs:29–38`) требует только инструмент, а кирку, топор
и удочку получает при создании каждый бот. Воин с нулём Mining получает оценку до 0.65,
идёт копать, четыре пустые цепочки подряд дают `Failed`, и `GatherAtSpotAction` штрафует
хорошую точку на 15 минут для всех. У ремёсел порог есть (`CrafterSkill = 20`).

### B-23. Прочее мелкое `[КОД]`

- `MahaonBotBeacon`: таймер `Timer.DelayCall(SpawnTick, SpawnTick, TrySpawnOne)` не
  сохраняется в поле и не останавливается в `OnDelete` — после удаления маяка тикает вечно.
- `BuildHouseGoal.Wants` не учитывает городскую квартиру (`HomeOf` её не видит), а
  `BuyCityHomeGoal` не учитывает гильдейский дом — бот может держать и квартиру, и дом.
- `WorldCatalog`: отрицательный результат поиска печи, кузницы, прялки запоминается
  навсегда (`ForgeSearched`, `SmithySearched`, `TextileSearched`) — поставленную GM-ом
  позже печь боты не увидят до рестарта. У `Placed` перепроверка раз в 10 минут есть.
- `SocializeGoal.FindPartner` выбирает ближайшего, даже идущего по делам; собеседник не
  останавливается, инициатор гоняется за ним.
- `BotParty._hired` (оплаченные часы найма) — только в памяти: рестарт съедает оплату;
  записи удалённых ботов не чистятся.
- Точки с `range 0`, общие для всех (`WorldCatalog.TryGetSmithy`, точка добычи в
  `GatherGoal.Plan`), — боты набиваются в одну клетку.
- `BuyBlueprintAction`, `GuildDonateAction`, `CityGuardCommandAction` выполняются откуда
  угодно, без похода в лавку, к банкиру, к камню — расходится с «честной симуляцией».
- `HuntAction`: исчезнувшая (despawn) добыча засчитывается как убийство.

### B-24. Посадки без потолка `[ГИПОТЕЗА]`

`SowGoal`/`PlantTreeAction`: каждый бот весной и летом сеет до 8 грядок за выход и
изредка сажает дерево. В коде ботов нет лимита ни на бота, ни на шард. Проверить, есть ли
потолок и вывод из оборота в `MahaonFarming`/`MahaonCropTile`; если нет — число предметов
вокруг городов растёт без предела (та же проблема, что была с DeathRobe).

## 5. Ошибки проектирования

**D-01. Нет сторожа от «стоит столбом».** По комментариям в коде этот симптом чинили
точечно минимум пять раз (`LastResort`, `LoiterGoal`, `GatherAction.Relocate`,
`BotSpeech.Ambient`, сироты маяка). Нужен общий механизм: бот не сдвинулся и не завершил
ни одного действия N минут — дамп мозга в лог (цель, действие, оценки) и принудительный
выход, вплоть до переноса домой. Сейчас бот в клетке вне навигационного графа
(`NavMapGraph.Locate` ищет в радиусе 3) проваливает любой `GoTo` бесконечно, и
восстановления нет — в `Systems/Bots` нет ни одного `MoveToWorld` для самого бота.

**D-02. Остатки читов v1 против принципа «без компромиссов».** Мана ×0.1
(`Spell.ScaleMana`, `Spell.cs:700–705`; `SpecialMove.ScaleMana`, 75–80), запас маны мага ×3
(`PlayerMobile.ManaMax`, 660–663), уворот вора 30% (`PlayerMobile.Damage`, 2954–2961). При
этом `BotSpellbook.Usable` и `TryCast` сравнивают ману с *полной* ценой: бот считает
дорогим то, что ему почти бесплатно. Исключение для реагентов уже убрано — эти остались.
Либо убрать, либо записать в дизайн-документ как осознанные.

**D-03. Мозг сохраняется частично.** Сериализуются дом, характер, три потребности и маяк.
Цель, обиды, метки добычи, свой труп, наём, прочитанные доски, паузы целей — теряются.
В дизайне (§2, причина №4; §3.7 «личная память») заявлено обратное. Минимум к сохранению —
то, от чего зависят деньги и вещи (B-07, наём).

**D-04. Экономика односторонняя.** Боты выставляют лоты на аукцион, но сами там не
покупают: в `Systems/Bots` единственное обращение к покупке — казна города
(`CityGuardUpkeep` → `TryBuyForGuild`). Непроданное возвращается в банк, бот забирает и
выставляет снова — круг без стока. Ремесленнику и снабжению стоит сначала смотреть аукцион
своего города.

**D-05. Отношения не остывают.** `BotRelationships` только копит счёт в пределах ±10.
Война гильдий заставляет бойцов нападать друг на друга (`FindPlayerThreat` → `IsAtWar`),
что углубляет вражду; условие остывания (`|среднее| ≤ 0.5`) недостижимо. Нужен распад во
времени.

**D-06. `Plan()` с побочными эффектами.** Цели объявлены «без состояния», но
`LeadGroupGoal.Plan` создаёт отряд, `BankGoal.Plan` и `TravelGoal.Plan` говорят реплики,
`CraftGoal.Score` через `TryPick` меняет выбранный материал в контексте ремесла. `Plan`
вызывается и при перепланировании после отказа. Побочные эффекты перенести в `Start`
первого действия.

**D-07. Продажность выводится из типа предмета и меток в памяти** (B-03, B-07). Нужен
один явный источник: «это бот добыл или сделал на продажу».

## 7. Предлагаемый порядок работы

1. **T-01** — чтобы базовая линия была зелёной (91 из 91).
2. **B-01** — одна правка в движке, от неё зависит осмысленность всего остального.
3. **B-03** — защита имущества игрока; до исправления `[BecomeBot` лучше не пользоваться
   на персонаже с вещами в банке.
4. **B-02**, **B-21**, **B-12**, **B-11** — устойчивость цикла решений.
5. **B-04**, **B-05**, **B-08** — бой.
6. **B-06** — после решения владельца, какой вариант правил ПК выбрать.
7. **B-07** + **D-03** — сохранение (смена версии `BotBrain`, миграция).
8. **B-09**, **B-10**, **B-13…B-24** — по одному, каждый со своим тестом.
9. **P-01…P-11** — после появления замера: сначала добавить в `[BotStats` опоздание
   пробуждений и время `ReviewGoal`, потом оптимизировать по цифрам.
10. **D-01** (сторож) можно делать параллельно с п. 4 — он же даст диагностику для
    остального.

Вопросы, которые решает владелец шарда, а не исполнитель: B-06 (правила ПК), D-02
(оставлять ли читы), D-04 (должны ли боты покупать на аукционе), B-24 (потолки посадок).

## 8. Что в системе сделано хорошо (не ломать)

- Связка «полезность → план → рефлексы» и отдельный слой `BotCombat` поверх плана.
- `BotScheduler`: пробуждение по заявке, бюджет на тик, штампы против устаревших записей,
  удаление сирот с освобождением слота маяка.
- `NavRouteWorker`: поиск на неизменяемом снимке, результат всегда возвращается (в том
  числе при исключении), пауза на время сохранения.
- Действия через штатные механизмы игры (`OnBuyItems`, `OnSellItems`, `CraftItem.Craft`,
  цели-курсоры предметов) — боты не обходят правила.
- `BotSpellbook`: шанс каста считается по формуле движка, а не по угаданным порогам.
- `HuntSpot.Crowd` — разведение охотников по местам.
