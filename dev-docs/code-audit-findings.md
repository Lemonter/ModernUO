# Аудит кода Mahaon — найденные баги и нестыковки

Полная ревизия всего кастомного кода шарда (запрошено владельцем: много кода написано в
Low-режиме и никогда не перепроверялось). Правило: **ничего не чинить сразу**, только
фиксировать находки — разбираемся по очереди отдельно. Статусы: `[ ]` не разобрано,
`[x]` разобрано/исправлено, `[skip]` осознанно не трогаем.

Результаты приходят от параллельных фоновых ревью-агентов по подсистемам, добавляются по
мере поступления.

## Блок 9: Items/Misc/Mahaon, гампы, стражники, CharacterCreation, House Rebuild/Fence

### [x] 1. ВЫСОКИЙ — MahaonTownDefenderMage не получает капа урона "показательного боя"
**Файл:** `Systems/MahaonRaids/MahaonRaidCombat.cs:42-43` (корень), затрагивает
`Mobiles/Guards/MahaonTownDefenderMage.cs:63-66` и `Mobiles/Guards/MahaonTownDefender.cs:80-83`.

```csharp
var attackerIsDefender = attacker is MahaonTownDefender;
var defenderIsDefender = defender is MahaonTownDefender;
```
`MahaonTownDefenderMage` — сиблинг-класс (`: BaseCreature`), НЕ наследник
`MahaonTownDefender`, поэтому `is MahaonTownDefender` для него всегда `false`.
`MahaonRaidSpawner.cs:106` намеренно подмешивает треть mage-защитников в бои набегов именно
ради капа урона (комменты в обоих файлах утверждают "той же логике/same logic") — но проверка
их тихо исключает: маги-защитники обмениваются полным, некапнутым уроном вместо задуманного
капа 1-2, что ломает саму суть системы (долгий фарм-спектакль вместо one-shot'ов).
**Похоже на исправление:** `attacker is MahaonTownDefender or MahaonTownDefenderMage`
(аналогично для `defender`).
**Исправлено:** добавлен маркер-интерфейс `IMahaonTownDefender`, оба класса теперь его
реализуют, `CapIfSpectacleFight` проверяет интерфейс вместо конкретного класса.

### [x] 2. ВЫСОКИЙ — VialOfBlood тратит гем и кровь до подтверждения успеха сокетирования
**Файл:** `Items/Misc/Mahaon/VialOfBlood.cs:54-110`.

`BloodGemSelectTarget.OnTarget` (54-69) сразу делает `gem.Consume(); _blood.Consume();`

успешной ветки `TrySocket`.
**Исправлено:** ресурсы больше не тратятся в `BloodGemSelectTarget`, `Consume()` вызывается
только внутри успешной ветки `TrySocket` в `BloodGemSocketTarget`.

### [ ] 3. СРЕДНИЙ (пока не проявляется) — коллизия ID кнопок в MahaonSaplingAddGump
**Файл:** `Gumps/MahaonSaplingAddGump.cs:200` (кнопка "назад" = 9998), `:209/215`
(пагинация = `9990 + page ± 1`).

Если у категории будет ≥9 страниц (~81+ пунктов), кнопка "следующая страница" получит тот
же ID 9998, что и "назад в главное меню" — а проверка `buttonId == 9998` идёт РАНЬШЕ общего
диапазона `9990..9999`, так что клик "дальше" тихо кинет в главное меню. Сейчас ни одна
категория (виды деревьев, урожай, маркеры данжей) близко не подходит к 81 пункту, но
коллизия реальная и всплывёт молча при росте списка.
**Похоже на исправление:** вынести кнопку "назад" из диапазона `9990-9999` (например, 9989).

### [x] 6. КРИТИЧНО — стили метательного оружия (Throwing) вообще недоступны игроку
**Файл:** `Network/Packets/IncomingMahaonPackets.cs:38`
```csharp
if (styleByte > 6 || categoryByte > (byte)WeaponCategory.Archery)
```
`WeaponCategory` (`WeaponStyleSystem.cs:6-14`): `Wrestling=0, Swords=1, Macing=2, Fencing=3,
Archery=4, Throwing=5`. Потолок проверки — `Archery` (4), поэтому пакет с
`categoryByte==5` (Throwing) тихо отбрасывается. Это ЕДИНСТВЕННАЯ точка вызова
`WeaponStyleSystem.SetActiveStyle` во всём коде (гампа-фолбэка нет) — то есть все стили
метательного оружия (Меткий бросок, Отравленные лезвия, Шквал клинков и т.д., все 6
описаны в `WeaponStyleSystem.cs:208-217`) физически недостижимы, юзеры Throwing навечно
заперты на стиле 0. Явный хвост от добавления Throwing как 6-й категории задним числом.
**Похоже на исправление:** потолок — `(byte)WeaponCategory.Throwing`.
**Исправлено:** граница проверки заменена на `(byte)WeaponCategory.Throwing`.

### [x] 7. КРИТИЧНО — бонус урона огнём/разрушением Magery утекает на ВСЕ школы магии
**Файл:** `MagerySchoolSystem.cs:157-165` (`GetDamageScalar`), дёргается из
`Spells/Base/SpellHelper.cs:1049-1050`.

`NecromancySchoolSystem`/`MysticismSchoolSystem`/`SpellweavingSchoolSystem.GetDamageScalar`
все начинаются с проверки "это точно заклинание моей школы?" — только
`MagerySchoolSystem.GetDamageScalar` такой проверки не делает вообще, принимает голый
`bool isFireDominant` без ссылки на само заклинание. `SpellHelper.Damage` — общая точка
урона для ВСЕХ школ (Necromancy, Mysticism, Spellweaving, Chivalry, SkillMasteries —
все туда стучатся), и она безусловно домножает урон на
`MagerySchoolSystem.GetDamageScalar`, независимо от того, какая школа реально кастовала.
Любой персонаж с прокачанным Fire/Destruction в Magery получает этот бонус на урон от
Necromancy/Mysticism/Spellweaving/Chivalry заклинаний тоже, даже если Magery почти не
использует.
**Похоже на исправление:** `GetDamageScalar` должен принимать `ISpell` и сам проверять
`SchoolOf(spell) is MagerySchool.Fire or MagerySchool.Destruction`, как у трёх соседей.
**Исправлено:** сигнатура теперь принимает `ISpell spell`, добавлен `SchoolOf(spell) ==
null` гейт, вызов в `SpellHelper.cs` обновлён.

### [x] 8. ВЫСОКИЙ — бонус засады "Ассасин" у Fencing даётся один раз НАВСЕГДА, а не за бой, плюс утечка памяти
**Файл:** `WeaponStyleSystem.cs:299,301-322`

/ смерть), не хранить вечно.
**Исправлено:** `HashSet` заменён на `Dictionary<(Mobile,Mobile), DateTime>` с 30-секундным
окном (`AmbushWindowSeconds`) вместо вечного бана пары.

### [x] 13. КРИТИЧНО — проверка "хватает ли маны" у ботов-магов делит реальную стоимость на 10, системно ~39 мест
**Файлы:** `BotMageAI.cs` (35 мест), `BotController.cs:824`, `BotCombat.cs:336,386`.

Везде вида `bot.Mana >= new XSpell(bot).GetMana() / 10`. `Spell.GetMana()` возвращает
реальную немасштабированную стоимость, а движковый `Spell.Cast()` требует полную
`ScaleMana(GetMana())`, не десятую часть. Бот проходит свою проверку при ~10% реальной
цены, зовёт `Cast()`, движок молча отказывает (маны не хватает), бот просто теряет тик
решения вместо того чтобы попробовать что-то подешевле — `return` идёт сразу после
`Cast()` независимо от результата. Затрагивает почти весь кастинг магов (хилы, баффы,
эскейп, урон, некромантию), паник-каст Ninjitsu MirrorImage, самохил воина CloseWounds.
**Похоже на исправление:** проверка должна быть `bot.Mana >= new XSpell(bot).GetMana()`.
**Исправлено:** все ~39 вхождений `GetMana() / 10` заменены на `GetMana()` в `BotMageAI.cs`,
`BotCombat.cs`, `BotController.cs`.

### [x] 14. ВЫСОКИЙ — BotGear.ApplyRememberedGearBonus качает не тот стат брони и путает единицы у оружия
**Файл:** `BotGear.cs:100-129`.

Броня: сравнивает запомненный лучший AR с текущим, разницу добавляет в
`armor.PhysicalBonus` — но `PhysicalBonus` влияет только на `PhysicalResistance`, вообще
не читается в расчёте `ArmorRating`/`ArmorRatingScaled`. Весь механизм "вернуть AR
воскрешённого бота до лучшего уровня" (ради которого это вообще написано, взамен старой
системы с утечкой ~1М предметов) не работает вообще — вместо этого раздувает физрезист
на несвязанную, некапнутую величину при каждом возрождении.
Оружие: добавляет сырую разницу урона (флэт-очки) прямо в `AosAttribute.WeaponDamage` —
а это ПРОЦЕНТНЫЙ бонус с капом ~100%. Разные единицы складываются вместе.
**Похоже на исправление:** для брони — трогать `armor.BaseArmorRating` напрямую (есть
публичный сеттер), для оружия — `weapon.MinDamage`/`MaxDamage` напрямую.
**Исправлено:** броня теперь бустит `BaseArmorRating` (через `ArmorScalar`), оружие делит
флэт-разницу между `MinDamage`/`MaxDamage` напрямую.

### [x] 42. ВЫСОКИЙ — BodyGuardSpell: формула раздела урона использует не тот операнд
**Файл:** `BodyGuardSpell.cs:213-231`.
```csharp
damage -= (int)(damage * mod);
var casterDamage = damage - (int)(damage * (mod - .05));
```
`casterDamage` считается от УЖЕ уменьшенного `damage`, а не от исходного удара. Тултип
обещает "телохранитель получает (block%+5)% всего урона" (от исходного), а по факту
формула даёт `D*(1-mod)*(1.05-mod)` вместо `D*(mod+0.05)`. При block%≈50 телохранитель
реально забирает ~27.5% вместо заявленных ~55%, и зависимость переворачивается — чем
выше block%, тем МЕНЬШЕ (не больше) забирает телохранитель.
**Исправлено:** `casterDamage` теперь считается от снятого до мутации `originalDamage` как
`(int)(originalDamage * (mod + .05))` — прямое соответствие формуле из тултипа.

### Команда `[TelGen` (генератор порталов, `Data/teleporters.json`)

Сверил байт-в-байт с текущим апстримом ModernUO (`modernuo/ModernUO`, ветка `main`,

телепорты жёстко зашиты в C#-скриптах, это чисто ModernUO-механизм.

Но нашёл кое-что реальное: **16 пар записей (32 из 1368) используют абсолютно

недостижимой с этой клетки. Похоже на опечатку координаты в самих данных ModernUO (судя
по соседним "парным" телепортам, которые правильно используют РАЗНЫЕ соседние клетки —
похоже, один из дублей должен был указывать на клетку рядом, а не на ту же самую).
